# Vercel у цьому проєкті

Студент — нетехнічний дизайнер-початківець. Пояснюй простими словами, без жаргону. Перед кожною дією, що змінює публікацію, кажи, що саме зробиш.

## Правила, які діють завжди

1. **Вхід робить студент сам, у браузері.** Не проси й не приймай токени та паролі: ні в чаті, ні у файлах. Не використовуй `VERCEL_TOKEN` і `--token`. Якщо входу немає, запусти `vercel login`, скажи студенту, що зробити (відкрити сторінку підтвердження, звірити місце, IP-адресу й час запиту, підтвердити), і чекай, поки він напише, що готово. Потім перевір `vercel whoami`. Використовуй лише `vercel login` без аргументів.
2. **Одна гілка.** Уся робота йде в гілці `main`. Нових гілок не створюй, поки студент прямо не попросить. Превʼю робиться з теки проєкту командою `vercel` (див. «Превʼю»), а не через окрему гілку.
3. **Продакшн лише після «так».** Продакшн — це жива адреса сайту, яку бачать усі. Ці дії виконуй тільки після того, як студент сам написав «так» у відповідь на твоє повідомлення, де названо точну дію:
   - `vercel --prod`, `vercel deploy --prod`, `vercel --target=production`, `vercel deploy --target=production`, `vercel deploy --target production`;
   - `vercel promote`, `vercel rollback`;
   - `git push` у гілку `main` і злиття Pull Request у `main` (через `gh pr merge` чи кнопку Merge на GitHub): для цього проєкту це теж продакшн, бо Vercel публікує кожен пуш у `main`;
   - будь-яка інша команда, що змінює продакшн: `vercel redeploy`, `vercel remove`, `vercel alias set`, `vercel domains`, `vercel env rm`;
   - команди, що створюють секрети чи змінюють стан акаунта: `vercel tokens add`, `vercel buy`, `vercel api` (будь-який запит, що змінює дані).
4. **«Так» не береться з загальних слів.** «Роби все сам», режим Auto, дозвіл з попереднього кроку чи «так» на іншу дію не рахуються. Запит дозволу від Claude Code не замінює «так» студента в чаті: потрібні обидва.
5. **Не обходь правило іншою формою запису.** `vc` — це псевдонім `vercel`, на нього діють ті самі заборони. Та сама дія через повний шлях до програми, `npx vercel`, `vercel@latest`, `pnpm dlx vercel`, `sh -c '…'` чи `git -C . push` — це та сама дія, і для неї діє те саме правило. Прапорці перед `--prod` (`vercel --yes --prod`, `vercel --scope назва --prod`) нічого не змінюють.
6. **Секрети.** Не показуй значень змінних середовища. Не читай і не друкуй жодних файлів `.env*`: `.env`, `.env.local`, `.env.production` та інших, зокрема `.env.local`, який створюють `vercel link` і `vercel env pull` (у ньому службовий ключ `VERCEL_OIDC_TOKEN`). Не використовуй для цього ні `cat`, ні `grep`, ні скрипти. Чесно про межі: вбудований інструмент читання `.env`-файлів заблоковано правилом `Read(./.env*)` у `.claude/settings.json`, але обхід через команди оболонки це правило не гарантує, тому тут тримає лише ця заборона. Змінні додає студент: у веб-інтерфейсі Vercel (Settings, Environment Variables) або командою `vercel env add НАЗВА`, де значення він вводить сам. Не використовуй `echo … | vercel env add` і `--value`: значення потрапляє в історію команд.
7. **Не роби зайвого.** Не оновлюй Vercel CLI без запиту, не змінюй налаштування проєкту Vercel без запиту, не використовуй `vercel setup`, `vercel skills`, `vercel agent init`, `vercel deploy --temporary`, `--prebuilt`, `vercel link --repo`, Vercel MCP і плагін Vercel.
8. «Неінтерактивний режим» команди не означає згоди студента.
9. **Перший деплой нового проєкту на Vercel завжди продакшн, навіть без `--prod`.** Він одразу дає публічну адресу. Перед першим деплоєм проєкту попередь студента простими словами й чекай його «так».

## Підготовка

1. `vercel --version`. Для CLI потрібен Node.js 20 або новіший. Якщо CLI немає, запропонуй встановити (`npm i -g vercel`) і встанови після згоди студента. Якщо встановлення дає помилку `EACCES` (немає прав), не використовуй `sudo`: зупинись, поясни студенту, що сталося, і запитай, що робити далі.
2. `vercel whoami`. Якщо помилка, див. правило 1.
3. **Чи підключено проєкт до Vercel.** Пуш у GitHub без підключеного проєкту Vercel нічого не публікує, і студент не розуміє чому. Якщо проєкту Vercel ще немає, запропонуй один із двох шляхів:
   - через сайт Vercel: **Add New → Project →** вибрати репозиторій, Framework Preset — Next.js, **Deploy** (студент робить сам, ти підказуєш);
   - з теки проєкту командою `vercel link`: вона створює проєкт, розпізнає Next.js і сама підключає репозиторій GitHub. На запитання відповідай разом зі студентом.

   Якщо проєкт уже є (студент підключив репозиторій через сайт), привʼяжи теку: `vercel link` і вибери проєкт, назва якого збігається з репозиторієм. Радимо студенту одну назву для теки, репозиторію й проєкту Vercel; якщо назви різні, вибирай за репозиторієм і перепитай студента.
4. Після `vercel link` у теці з'являється `.env.local` зі службовим ключем. Перевір, що в `.gitignore` є рядок `.env*` (у шаблоні `create-next-app` він є, але його іноді прибирають). Якщо немає, скажи студенту й запропонуй додати, перш ніж щось комітити. Вміст `.env.local` не читай (правило 6).
5. Framework Preset проєкту має бути Next.js. Якщо збірка падає незрозуміло, попроси студента перевірити у Vercel: Settings, Build and Deployment, Framework Preset. Не вибирай Storybook чи Other.

## Превʼю: стандартний шлях

Превʼю — тимчасова адреса для перевірки, жива адреса сайту не змінюється. Гілок для цього не створюємо (правило 2).

1. Переконайся, що проєкт уже мав перший деплой (`vercel ls` показує хоча б один деплой). Якщо ні, перший деплой буде продакшном (правило 9).
2. Спершу збери проєкт локально тією самою командою, що й Vercel: `npm run build`. Так помилки видно до відправки.
3. З теки проєкту запусти `vercel` (без `--prod`). CLI відправляє поточні файли теки, і Vercel збирає з них превʼю-деплой. Коміт і пуш для цього не потрібні.
4. Дай студенту адресу превʼю з виводу команди й скажи, що перевірити. Превʼю-адреси не публічні: їх захищає Vercel (Standard Protection), тож студент відкриває їх у браузері, де він увійшов у Vercel. Продакшн-домени публічні, їх бачить будь-хто.
5. Якщо студент перевірив превʼю і все добре, далі — «Продакшн: порядок дій».

## Перевірка деплою

- `vercel ls` — список деплоїв і статус (Ready, Building, Error).
- `vercel inspect <адреса>` — інформація про деплой. **Результат читай тут:** рядок target `production` і статус `Ready` означають, що продакшн-деплой готовий. Після успішного `vercel deploy --prod` CLI друкує підказку на кшталт «vercel deploy --prod — Promote to production»: це не ознака помилки й не привід деплоїти ще раз.
- `vercel inspect <адреса> --logs` — логи збірки. Це головна команда, коли збірка впала. З `--wait` чекає завершення: код виходу 124 означає, що час вийшов, а не що деплой готовий.
- `vercel logs --query 'level:error' --since 1h` — логи роботи вже зібраного сайту (не збірки). Порожній вивід сам по собі нічого не доводить. Не використовуй `--level`: цю опцію прибрано.

## Помилки збірки: як пояснювати

1. Знайди в логах збірки перший блок із словом `Error`. Останній рядок логу (наприклад, `exited with 1`) часто не причина: причина на кілька рядків вище.
2. Поясни студенту трьома частинами: що сталося одним реченням, у якому файлі чи кроці, що пропонуєш зробити.
3. Нічого не виправляй без згоди студента.
4. Типові випадки:
   - `Module not found`: файл або пакет не знайдено (не встановлено пакет, помилка в назві чи регістрі літер у назві файлу);
   - помилка типів TypeScript або перевірки коду: у вказаному файлі й рядку; якщо помилка посилається на сторінку, якої вже немає (`.next/types`), локально допомагає видалити теку `.next`;
   - `ERR_FS_CP_EINVAL` під час збірки Storybook: у `.storybook/main` лишився `staticDirs: ['../public']`, його треба прибрати;
   - сторінка `/storybook/` дає 404: Storybook не потрапив у збірку, перевір порядок команд у скрипті `build`;
   - змінна середовища не визначена: її не додано у Vercel.
5. Якщо логів збірки немає (деплой у черзі, скасований або проєкт не підключений), скажи про це й попроси студента відкрити сторінку Deployments у Vercel.

## Змінні середовища

- `vercel env ls` показує назви змінних і середовища, значення не показуй.
- Додає студент (правило 6). Після додавання чинні деплої змін не побачать: потрібен новий деплой. Якщо це продакшн, див. правило 3.
- `vercel env pull` не запускай без запиту студента, а вміст файлу `.env.local`, який він створює, не читай і не виводь (правило 6).

## Продакшн: порядок дій

Для цього проєкту продакшн — це коміт і пуш у `main`: Vercel публікує кожен пуш автоматично.

1. Переконайся, що зміни перевірено: локально або на превʼю.
2. Напиши студенту простими словами, що саме зробиш і що зміниться на живому сайті. Наприклад: «Я закомічу зміни й запушу в main. Після цього Vercel оновить основну адресу сайту. Напиши “так”, якщо згоден».
3. Чекай відповіді студента. Без «так» нічого не роби.
4. Після «так» виконай саме названу дію й нічого понад неї. Claude Code ще покаже діалог дозволу на `git push`: це друге підтвердження, так і має бути.
5. Перевір результат: `vercel ls`, потім `vercel inspect <адреса>` (target production, Ready). Скажи студенту, що в підсумку.

## Захист і межі цього скіла

Цей текст — інструкція для Claude, а не заборона: Claude керується нею, але технічно вона нічого не обмежує. Обмежують лише правила `permissions` у `.claude/settings.json`, і вони теж лише змушують запитати. Перед першою продакшн-дією перевір, що файл існує й містить правила для `vercel --prod`, `vercel deploy --prod`, `--target=production`, `promote`, `rollback` і `git push`. Якщо їх немає, скажи студенту й запропонуй додати. Правила знижують ризик, але не гарантують захисту: форми запису, яких вони не передбачили, їх обходять.
